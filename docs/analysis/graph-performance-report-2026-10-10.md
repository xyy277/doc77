# 图谱性能实测诊断报告（2026-10-10）

> 触发背景：用户反馈"前期加了太多功能在 doc77 内部，特别是图谱，虽经几次优化仍有卡顿"。
> 方法：本机实测（Windows + system Chrome headless + 合成大图谱项目），全部数字可复现。
> 基线版本：`1.1.10`（771648a）——本次从 v1.0.8 拉取至最新后首次实测。
> 语言规范：专业术语英文，其余中文（见根 CLAUDE.md）。

---

## 0. 结论摘要（TL;DR）

按**影响面 × 修复成本**排序，图谱卡顿有 5 个独立成因，其中前 2 个建议立即处理：

| # | 问题 | 实测证据 | 影响 | 修复成本 |
|---|---|---|---|---|
| **1** | **`app.css` 引用 Google Fonts 外链（渲染阻塞）** | 外链不可达时首屏 **DCL 254ms → 5136ms**，canvas 首帧 1.34s → **5.48s** | 🔴 极高（全站页面，国内网络必现） | 极低（删一行 @import 改系统字体栈） |
| **2** | **服务端无任何响应压缩** | `/api/graph` 5000 节点返回 **1.25MB 未压缩 JSON**；10000 节点 **2.51MB** | 🟠 高（LAN/移动端/大图谱） | 低（引入 compression 中间件） |
| **3** | **全量索引耗时线性增长 + 事件循环停顿** | 10k 文件索引 **12.09s**，单次事件循环停顿 **211ms** | 🟠 中（进入项目卡顿、UI 冻结感） | 中 |
| **4** | **Canvas 逐节点绘制未批量化** | 5000 节点单帧 11.05ms，其中节点绘制 8.87ms；批量绘制可降至 4.08ms（**2.2x**） | 🟠 中（大图交互余量小） | 中 |
| **5** | **力导向模式下拖拽节点触发物理引擎全速运行** | 2000 节点拖节点 **主线程占用 78.4%**；拖拽结束静置 3s 仍占用 998ms（33.3%） | 🟡 中（卡顿体感的主要来源） | 低 |

**一句话结论**：图谱本身的算法与 API 层已不是瓶颈（服务端 5000 节点 API 仅 70ms、hitTest 仅 0.01ms）；
当前卡顿主要来自**外部字体阻塞首屏**与**渲染/物理层的持续性开销**，属于"工程优化"而非"架构重做"。

| 项 | 值 |

| 机器 | 本机（Windows，NAT 后），Node 22.22.2 |
| 数据库 | better-sqlite3 12.11.1（WAL），临时 DB（每规模冷启动） |

**指标口径**

- **主线程占用率** = 交互期间 CDP `TaskDuration` 增量 ÷ 真实耗时。**这是与合成器/帧率无关的硬指标**：
  接近 100% 意味着主线程饱和，用户端必然掉帧。
- rAF 帧率（fps / p95 / 掉帧数）作为辅助参考；headless 合成器可能节流 rAF，
  故以主线程占用率为准。

## 2. 服务端实测

### 2.1 规模曲线

| 规模 | 全量索引 | 事件循环最大停顿 | `/api/graph` | payload | 单节点成本 |
|---|---|---|---|---|---|
| 500 | 0.64s | 82ms | 13ms | 128KB | 1.3ms / 256B |
| 1000 | 1.21s | 88ms | 23ms | 256KB | 1.2ms / 256B |
| 2000 | 2.88s | 92ms | 36ms | 512KB | 1.4ms / 256B |
| 5000 | 6.70s | 158ms | 70ms | 1.25MB | 1.3ms / 250B |
| 10000 | 12.09s | 211ms | 214ms | 2.51MB | 1.2ms / 251B |

**读法**：索引与 payload 都随规模**严格线性**，没有指数级劣化 —— 说明数据层（v15 doc_meta/doc_links + 索引）设计是健康的。
两个待改进点：

1. **payload 未压缩**：10000 节点 2.51MB JSON 裸传。gzip 后同类 JSON 通常降到 10-15%（≈300KB）。
   本机/局域网影响小，但**手机端（移动伴侣）与隧道场景**会明显拖慢。
2. **索引期事件循环停顿 211ms**（10k 文件）：虽然批处理已让出（`setTimeout(0)`），但单次停顿仍超
   100ms 感知阈值。进入项目后立即操作会有"顿一下"的感觉。

### 2.2 其他接口（5000 节点）

| 接口 | 耗时 | payload |
|---|---|---|
| `/api/graph/stats` | 13-17ms | 158B |
| `/api/graph/orphans` | 5-22ms | 39B |
| `/api/graph/broken` | 7-11ms | 1.4KB |
| `/graph`（HTML） | 3ms | 7.6KB |

洞察类接口全部 <25ms，**不是瓶颈**。

## 3. 前端交互实测（主线程占用率）

### 3.1 各规模对比（每项 3 秒连续操作，180 次事件）

| 操作 | 500 节点 | 2000 节点 | 5000 节点 | 10000 节点 |
|---|---|---|---|---|
| 拖拽平移（pan） | **7.9%** | 7.6% | **25.5%** | **41.6%** |
| 滚轮缩放 | 5.0% | 7.9% | **26.4%** | **45.7%** |
| 悬停移动（hover） | 5.1% | 8.3% | **17.7%** | **27.6%** |
| 拖拽节点 | 5.1% | **78.4%** ⚠️ | 26.6% | **45.2%** |
| 力导向 + 拖拽 | — | — | 12.9% | **65.7%** ⚠️ |
| 力导向 + 缩放 | — | — | 15.0% | 21.5% |
| **交互后静置 3s** | 0% | **33.3%** ⚠️ | 0% | 0% |

（500/2000 走力导向自动布局；5000/10000 因 >2000 节点自动降级为网格布局，"力导向+"行为手动启用。）

### 3.2 三个明确结论

**① 500 节点以内完全流畅**：所有操作主线程占用 ≤8%，fps 60，零掉帧。
→ 小图谱（个人笔记库）体验没有问题，用户的卡顿感必然来自更大规模或首屏。

**② 节点数 ≥2000 后余量迅速消失**：

- 10000 节点（网格）平移 41.6%、缩放 45.7%，**已丢失 36 帧/3s**；
- 10000 节点启用力导向拖拽 → **65.7% 占用 + 25 次 long task 共 1.61s + fps 掉到 36**；
- 这是"毛球图拖不动"的量化形态。

**③ 两个反直觉现象（值得单独修）**：

- **2000 节点拖拽节点 = 78.4%**，而其平移只有 7.6% —— 差 10 倍。
  原因：拖节点会 `sim.alphaTarget(0.3).restart()`，**物理引擎在拖拽期间全速运行**；
  平移不碰物理引擎。2000 节点恰好是"自动力导向"的临界值，代价最高。
- **2000 节点交互后静置 3s 仍占用 998ms（33.3%）** —— 物理引擎在 `pointerup` 后继续收敛
  （alpha 从 0.3 衰减到 0.001 约需 1.3s），期间持续烧 CPU + 每 tick 重绘。
  用户主观感受就是"放开鼠标后页面还在卡"。

## 4. 绘制成本分解（微基准，5000 节点 / 10000 边）

单帧成本拆解（同样画布、同样节点分布，各重复 30 次取样）：

| 项目 | 现状实现 | 优化实现 | 收益 |
|---|---|---|---|
| 边绘制（一次 path + 一次 stroke） | 2.17ms | — | — |
| **节点绘制** | **8.87ms**（逐节点 `beginPath+arc+fill`） | **4.08ms**（按颜色合并 path） | **2.2x** |
| `byId` 每帧重建（draw() 内） | 0.545ms | 0（构建模型时建一次） | 100% |
| `hitTest` 线性扫描 | 0.0104ms | 0.007ms（网格索引） | 1.5x（**无必要**） |
| **单帧合计** | **11.05ms**（理论 90fps） | **6.25ms**（理论 160fps） | **1.8x** |

**两个反直觉结论，能省下无效工作量**：

1. **`hitTest` 不是瓶颈**：5000 节点线性扫描仅 0.0104ms/次（循环体极简）。
   引入四叉树/网格索引**收益可忽略**，不建议做。
2. **`byId` 每帧重建也不是大头**（0.545ms），但 **100% 是浪费** ——
   该 map 只在"边端点是字符串"（d3 加载失败降级）时才需要；
   正常 d3 模式下 `forceLink` 已把 source/target 替换为节点引用，
   `typeof e.source === 'string'` 恒为 false，**这个 5000 键对象每帧白建**。

真正的成本是 **5000 次独立的 `arc + fill` 调用**：Canvas 2D 的每次 `fill()` 都触发一次光栅化。
按调色板颜色（12 色 + 中性 13 组）合并成 13 个 path 再一次 `fill`，即在实测中省掉 4.8ms/帧。

## 5. 首屏加载诊断（最高优先级问题）

### 5.1 资源瀑布（2000 节点项目，冷启动）

| 耗时 | 开始 | 传输 | 类型 | 资源 |
|---|---|---|---|---|
| **248.5ms** | 83ms | 1042B | css | **`fonts.googleapis.com/css2?family=Inter...`** |
| 56.0ms | 42.5ms | 55KB | script | `/js/graph.js` |
| 53.7ms | 42.4ms | 79KB | script | `/js/common.js` |
| 39.1ms | 42.3ms | 68KB | link | `/css/app.css` |
| 27.7ms | 41.7ms | 501B | link | `/css/tailwind.css` |
| 23.9ms | 71.1ms | 0B | css | `/css/tailwindcss`（空响应，见 §7） |

主线程累计：Task 173ms / Layout 93ms / Script 14ms —— **JS 与布局都很健康**。

### 5.2 外链阻塞验证（决定性证据）

对 `fonts.googleapis.com` 注入 5s 延迟后失败（模拟被墙 / 离线）：

| 场景 | DCL | FCP | canvas 首帧 |
|---|---|---|---|
| 字体正常可达（基线） | 254ms | 1084ms | 1344ms |
| **字体 5s 后失败** | **5136ms** | **5348ms** | **5477ms** |

`packages/core/src/web/css/app.css:5`：

```css
@import url('https://fonts.googleapis.com/css2?family=Inter:wght@400;500;600;700&display=swap');
```

`@import` 是**渲染阻塞**的：浏览器在拿到该 CSS 前不会绘制首帧。
中国网络访问 `fonts.googleapis.com` 普遍超时 → **用户端"打开 doc77 先白屏 5 秒"**，
且与产品"本地优先 / 离线可用"的定位直接冲突。**这是全站问题（Dashboard / preview / graph 共用 app.css）**。

## 8. 建议的优化动作（按性价比排序）

### P0（建议立即做，收益最大、风险最低）

**1. 移除 Google Fonts 外链，改用系统字体栈**

```css
/* packages/core/src/web/css/app.css */
- @import url('https://fonts.googleapis.com/css2?family=Inter:wght@400;500;600;700&display=swap');
+ /* 系统字体栈：零外链、零阻塞、离线可用 */
+ font-family: -apple-system, BlinkMacSystemFont, 'Segoe UI', 'PingFang SC',
+              'Hiragino Sans GB', 'Microsoft YaHei', system-ui, sans-serif;
```

预期：DCL 恢复 254ms 量级，**消除最坏情况 5s 白屏**；同时让"离线可用"名副其实。
（如确需 Inter，可自托管 woff2 到 `/vendor` 并 `font-display: swap`。）

**2. 为服务端响应加 gzip**

引入 `compression` 中间件（或 Express 5 的等价方案），对 `application/json` / `text/*` 生效。
预期：2.51MB → 约 300-400KB，**移动端与隧道场景打开图谱明显变快**。
注意：SSE（`/api/events`）需排除，避免缓冲破坏流式语义。

### P1（收益明确，改动集中在 graph.js）

**3. 节点绘制批量化**
把 `draw()` 里的逐节点 `beginPath/arc/fillStyle/fill` 改为"按颜色分组 → 合并 path → 一次 fill"。
预期：5000 节点节点绘制 **8.87ms → 4.08ms**，单帧 11.05ms → 6.25ms（**1.8x**），
大图平移/缩放掉帧显著减少。

**4. 移除 `draw()` 内每帧重建的 `byId`**
改到 `buildGraphModel()` 时构建一次并挂在 model 上（或仅在边端点为字符串时惰性构建）。
预期：每帧省 0.545ms 且消除 5000 键对象的 GC 压力。

**5. 拖拽节点时收敛物理引擎**
`pointermove` 里对 `sim.alphaTarget(0.3).restart()` 做节流（例如仅在 >16ms 间隔调用），
或在 `pointerup` 后**主动加速收敛**（`sim.alphaTarget(0).alpha(0.05)` 或直接 `sim.stop()`）。
预期：消除"松手后还在卡 1.3s"的体感；2000 节点拖节点 78.4% 占用可大幅下降。

### P2（结构性改进，需评估）

**6. 索引批处理让出频率提升 / 增量覆盖**
把单次事件循环停顿从 211ms 压到 <50ms（对齐 `performance.test.ts` 里的既有目标）。

**7. 大图渲染 LOD（Level of Detail）**
缩放小于某阈值时不做每节点着色、不画标签、甚至用单色批量，
把"看全局结构"与"看细节"的成本分开。

**8. 图谱数据内存缓存 / ETag**
`/api/graph` 连续三次 88/95/103ms 稳定但无缓存；加 ETag 后重复进入可走 304。

## 10. 测量局限（避免误读）

1. **headless 合成器可能节流 rAF**：单次实测中出现过 rAF 掉到 4fps 的干扰（后台安装任务占用 CPU 期间）。
   因此本报告的**主指标是主线程占用率（CDP TaskDuration）**，fps 仅作参考。
2. **合成数据 ≠ 真实 vault**：环形互链（每节点 2 出链）比真实笔记的连接度更均匀；
   真实项目若存在超级枢纽节点（单节点数百入链），渲染成本分布会不同。
3. **冷启动口径**：每规模使用全新 DB，索引时间不含"已索引后增量"的快路径。
4. **同机回环**：服务端耗时不包含真实网络的 RTT 与带宽约束；
   这也意味着 **§2 的 payload 压缩收益在真实 LAN/移动端会更大**。
5. 一次早期实测（bench2）因后台任务干扰出现整体偏高的读数，已弃用；
   本报告采用干净环境复测数据（bench3/bench4 + probe）。
